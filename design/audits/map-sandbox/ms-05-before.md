## Assumptions

| Prompt says | Found |
| --- | --- |
| `startFromBuild(steps, groups, making)` | A Result is not a `Step` (MS-00): it is a `ListResult` the List draws from `results`, with `from`, the number of the step it came from. `startFromBuild` takes the Results as an optional fourth argument (`{ id, from }`), as `orderFacts` and `mapLinks` do. "The real kind name in `graph.ts`": there is none; `StepKind` has no result. |
| Sessions side by side come from `stages.ts` | `sessionMapFor` (in `sessionMap.ts`) already works out parts in order (`workstreamsOf`) and every session's stage (`stagesOf`, reading `withAbove` and `parallelWith` through `withAboveOf`). Inside a part, a run of sessions in one stage is one `across` split; the stages stack in a `down` split. |
| Implicit groups | `SessionGroup.implicit` (key `typed-legacy-0`); `shownGroups` leaves them out. Their tiles are found by `stepNumbers`. |
| Node ids | `newMapNodeId()` is random. The plain arrangement is worked out on every render (Decision 4), so its ids are made from the keys instead (`m-part-<key>`, `m-session-<key>`, `m-box-<key>`, `m-result-<id>`, ...): the same build gives the same layout every time, and selection survives a render. |
| `contrast` in `src/lib/theme/luminance.ts` | Yes (`contrast`, `over`, `parse`). Tokens are `var(--x)` strings, so the test resolves them with `resolveToken` (`resolve.ts`), as `partColour.ts` already does at run time. |
| Ink "a token where one fits" | The themes are declared on `:root[data-theme]` only, so a token on a dark canvas in the light theme would be dark ink on dark paint. The canvas is paint, not theme: `canvasRecipes.ts` re-declares the tokens on the canvas element from the theme that suits the background (`dusk` for grey, dusk and slate, `noon` for paper; a custom colour by its luminance). Every colour inside, tiles included, stays a `t.<token>` and reads right on the paint whatever the app's theme. The canvas matches `01-finished-map.png` (drawn in dark) in the light theme too. |
| The List's tile can't render outside the List (MS-00) | Confirmed: every card is module-private and takes `BuildListProps`. All their contexts have defaults, and `useNestTile` is disabled with no `NestContext`, so a card renders with stub props. Rather than splitting 2,900 lines of cards into presentational halves, `BuildList.tsx` exports `ListTile` (its own `card()` dispatcher, which the List now calls) and `ListResultTile`, and a `TileVariantContext` that the cards read: with `variant: "map"` they leave out the drag handle, the reorder controls in the menu (the whole List menu is replaced by the map's, none yet), the footer link, Uses chips, nest buttons and sent-with suggestions, take the badge's number from the map's scheme, and show only the parts in `show[tileId]`. `StepTile.tsx` is the map's entry point (`variant="map"`). No markup is copied. |
| `show[tileId]` parts | The List draws text, code and check criteria as each tile's body; files are the attachment strip; settings and picture have no List form yet (MS-10 adds them). So `text` is the body as the List draws it (a prompt's text, a code tile's well, a check's criteria and status), `files` the attachment strip. |
| `SessionMapColumn` head | Title (`mapTitle`: "3 sessions in 2 parts"); second line (`mapSummary` and the shown line: "Shown on build page" / "Not on build page"); direction switch (maker only, 768 and wider: Horizontal / Vertical, writes `making.map.direction`); Fit to screen (scales the drawing to the column, `aria-pressed`); Map options (maker only: Show on build page, a checkbox writing `making.map.onBuildPage`; Remove map, writing `making.map.on: false`). A reader's head has the title, the summary and Fit to screen. The new head keeps all of them but the direction switch. |
| `ReaderMap` | Draws `SessionMapColumn` and `SessionMapPanel` on wide screens, `PhoneMap` in a pinch well on phones. Phones are MS-13's: the phone map stays. Wide screens draw the canvas in reader mode in the same column head, with no panel, as in the composer. |
| Audits read a page list | `e2e/audit/support/harness.ts` `ROUTES`, read by both `contrast-sweep` and `theme-completeness`. `/dev/map-sandbox` is added there. |
