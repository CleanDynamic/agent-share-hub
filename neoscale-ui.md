## Project Overview

NeoScale AI is a React + TypeScript + Tailwind + Supabase application.
Routing: React Router v6.
Styling: Tailwind CSS utility classes + shadcn/ui components.
Build: Vite.
Deployment: Netlify via GitHub (main branch auto-deploys).

## Critical Implementation Rules

These rules exist because of specific past failures.
Breaking any of them will break the UI.

### RULE 1 — Inline styles for glass/visual effects only
Tailwind's generated styles override custom CSS classes at build time.
Any visual effect (background, backdropFilter, border, boxShadow,
borderRadius, color, transition) that needs to be precise MUST be
applied as an inline style={{ }} attribute directly on the JSX element.
Do NOT add new CSS classes to index.css and apply them — they will
be overridden by Tailwind.
Exception: @keyframes animations must be in index.css because inline
styles cannot define keyframes. Define the keyframe in index.css,
then reference the animation name in an inline style.

### RULE 2 — Never change structural properties
Do NOT change: position, width, height, overflow, zIndex, display,
flex, grid, gap, padding, margin on any existing layout element.
Only add visual properties: background, backdropFilter,
WebkitBackdropFilter, border, borderLeft, borderRight, boxShadow,
borderRadius, color, fontSize, fontWeight, opacity, transition.
Changing structural properties will break the three-panel layout.

### RULE 3 — Visual shell components are externally supplied
The following components are intentionally left as transparent shells.
Their visual treatment (glass panels, liquid metal surfaces, chrome
blobs) is imported externally by the developer — NOT generated by AI.
Do NOT attempt to add glassmorphism, blur, or chrome effects to:
  - AppLayout.tsx (panel containers)
  - LeftPanel.tsx (nav sidebar surface)
  - RightPanel.tsx (discovery sidebar surface)
  - BlobBackground.tsx (background animation)
  - Any primary button surface
These files must only contain structural/functional code.
Leave a clearly labelled import slot where the visual component goes.

### RULE 4 — Never install UI libraries without confirmation
Do NOT install liquid-glass-react, framer-motion, or any animation
library without explicit user confirmation. Past installs of
liquid-glass-react destroyed the layout by breaking CSS stacking
context on fixed-position elements.

### RULE 5 — Commit after every discrete change
Each commit must be independently revertable.
Never bundle unrelated changes into one commit.
Commit message format: "COMPONENT-N: description"

## Visual Shell Pattern

When building any component that will receive an external visual
treatment, structure it as a shell with a clearly labelled slot:

```tsx
// VISUAL SLOT — replace this div with your external glass component
// Props needed: className, style, children
// The div below is the transparent placeholder.
// When you have your glass component ready, swap this div out.
<div
  data-visual-slot="left-panel"
  style={{ position: 'relative' }}
>
  {children}
</div>
```

Use data-visual-slot="[name]" on every shell element so the
external component can be targeted precisely.

Slot names to use:
  "background"      — BlobBackground.tsx root div
  "left-panel"      — LeftPanel.tsx outer container
  "centre-panel"    — AppLayout.tsx centre column
  "right-panel"     — RightPanel.tsx outer container
  "feed-card"       — ContentCard.tsx outer div
  "bounty-card"     — BountyCard.tsx outer div
  "reblog-card"     — ReblogCard.tsx outer div
  "category-card"   — RightPanel.tsx category grid item
  "btn-primary"     — Any primary CTA button wrapper
  "btn-secondary"   — Any secondary button wrapper
  "modal-surface"   — Any modal or sheet overlay

## Component Conventions

### Feed Cards
All feed card components must accept:
  className?: string
  style?: React.CSSProperties
  data-visual-slot attribute on the outermost div

The outermost div must have NO hardcoded background colour.
Background is supplied either by the design system tokens above
(applied inline) or by the external visual component.

### Buttons
All button-like elements must:
  — Accept onClick, disabled, className, style, children props
  — Have data-visual-slot="btn-primary" or "btn-secondary"
  — NOT have hardcoded background colors in JSX className
  — Apply button styles via inline style={{ }}

### Modals and Sheets
All modals must:
  — Use the existing shadcn/ui Dialog or Sheet component as base
  — Have data-visual-slot="modal-surface" on the content wrapper
  — NOT override the shadcn background with a hardcoded colour

## Pipeline for UI Changes

When invoked, follow this pipeline:

### Phase 1 — Audit
Read the relevant component files. Identify:
  - What currently renders (structure)
  - What visual slots exist or need adding
  - Whether the change risks breaking structural layout
  - Which other components import the target component
Present findings. Ask for confirmation before proceeding.

### Phase 2 — Plan
Write out the exact changes:
  - Files to modify
  - Properties to add/change
  - Properties NOT to touch
  - New files to create (if any)
  - Commit strategy (one commit per logical unit)
Present the plan. Wait for approval before writing code.

### Phase 3 — Implement
Execute the approved plan.
Apply changes file by file.
After each file: confirm the change in a summary.
Do NOT make unrequested changes while in a file.

### Phase 4 — Verify
After all changes:
  - Confirm no structural properties were modified
  - Confirm all visual slots have data-visual-slot attributes
  - Confirm Supabase queries are untouched
  - Confirm routing is untouched
  - State which files were changed and what was changed in each

### Phase 5 — Commit
One commit per logical unit of work.
Format: "COMPONENT-N: description of visual change"
Never commit broken builds.
